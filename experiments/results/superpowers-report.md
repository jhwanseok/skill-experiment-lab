# 실험 보고서 — superpowers는 디버깅 프로세스를 실제로 개선하는가

**날짜**: 2026-08-12 · **대상**: [superpowers](https://github.com/obra/superpowers) (plugin) · **Archetype**: 디버깅/프로세스 · **픽스처**: `fixtures/bookmarks-api`
**원자료**: [실험설계](../design/superpowers.md) · [실행별 지표 전체](superpowers.md)

## 한 줄 요약

**버그를 정확히 고치는지는 superpowers 유무와 무관했다(OFF/ON 6세션 전부 근본 원인을 정확히 수정하고 유효한 회귀 테스트를 남겼다).** 하지만 **프로세스에는 실제 차이가 있었다** — ON 3세션 중 2세션이 아무 코칭 없이 스스로 `systematic-debugging` 스킬을 호출했고("버그 수정 → 이 스킬 먼저"라는 세션 시작 시 주입된 규칙을 근거로 직접 인용), 1세션은 실패하는 테스트를 먼저 커밋하고 수정을 별도로 커밋하는 진짜 RED→GREEN 패턴을 보였다. 그 대가로 비용·시간·턴 수가 30~43% 더 들었다.

## 핵심 질문과 방법

**핵심 질문**: superpowers(체계적 디버깅·TDD 프로세스 스킬)를 켰을 때 버그 수정 프로세스가 실제로 개선되는가 — 근본 원인까지 고치는지, TDD RED→GREEN 순서를 따르는지, 그리고 애초에 스킬 체인이 자발적으로 작동하는지.

- **픽스처**: `bookmarks-api-baseline`에서 분기해 `GET /bookmarks?sort=title`에 `COLLATE NOCASE` 없는 정렬 버그를 심고 재현 테스트는 없앤 `bookmarks-api-baseline-bug` 태그. 대문자로 시작하는 제목이 SQLite 기본 정렬(BINARY collation) 때문에 알파벳순과 무관하게 항상 앞에 온다.
- **티켓**: 에이전트 아키텍처에 대한 언급이 전혀 없는, 자연스러운 1인칭 버그 리포트 문장. OFF/ON 동일 문구.
- **조건**: OFF(superpowers 꺼짐) vs ON(켜짐), 둘 다 ponytail·caveman은 꺼서 변수 격리.
- **표본**: 조건당 3회, 총 6세션.
- **지표**: 근본 원인 수정 여부, 재현 테스트의 실제 유효성(버그 태그에 대고 돌려서 실패하는지 검증), `git log`의 RED→GREEN 커밋 패턴 — 전부 정성 판정. 보조로 비용·시간·턴 수·토큰.

## 진행 중 만난 함정들 — 이번엔 측정 방식 자체를 바꿔야 했다

이번 실험은 설계를 세 번 갈아엎었다.

**1차**: `Agent` 도구로 파견된 서브에이전트에게 `superpowers:systematic-debugging`을 명시적으로 강제 호출시키는 방식. 레포를 열어보니 이건 superpowers 전체가 아니라 개별 스킬 하나를 강제 주입한 효과만 재는 것이었다 — 폐기.

**2차**: "너는 파견된 서브에이전트가 아니라 주 세션이다, SUBAGENT-STOP은 적용 안 된다"고 프롬프트에서 직접 코칭하는 방식. 다시 보니 이건 모델에게 결론을("너는 서브에이전트가 아니다") 미리 정해주는 것이라, "superpowers가 자발적으로 발동하는가"가 아니라 "발동하라고 강요하면 발동하는가"를 재는 꼴이었다 — 폐기.

**3차**: 에이전트 아키텍처 언급을 프롬프트에서 완전히 빼고 자연스러운 1인칭 버그 리포트로만 티켓을 쓰는 방식. 이게 정직한 설계였지만, 활성화 검증 단계에서 더 근본적인 문제가 드러났다: **`Agent(isolation:"worktree")`로는 superpowers가 카탈로그에도 없고, `Skill` 도구로 이름을 직접 불러도 전부 `Unknown skill` 에러**였다. ponytail보다 심각한 실패 — ponytail은 최소한 카탈로그엔 나타나고 명시적 호출로 우회가 됐는데, superpowers는 이 하네스의 `Agent` 도구에는 아예 존재하지 않는 것으로 취급됐다.

**4차(채택)**: `Agent` 도구를 완전히 버리고, 진짜 최상위 세션인 헤드리스 `claude -p` CLI 프로세스(`--output-format json`)로 전환했다. `git worktree add`로 직접 격리 워크트리를 만들고 그 안에서 `claude -p`를 돌렸다. 스모크 테스트로 확인: OFF에서는 `using-superpowers` 내용이 전혀 없고, ON에서는 SUBAGENT-STOP을 포함한 전체 본문이 정상 주입됐다(`cache_creation_input_tokens`가 7,378→9,350으로 스킬 로딩 비용만큼 증가). 진짜 최상위 세션이라 "파견된 서브에이전트"에 해당하지 않아 SUBAGENT-STOP에 걸릴 근거도 없었다.

이 전환은 `Agent` 도구가 자동으로 주던 `subagent_tokens`/`tool_uses` 계측을 포기하고 `claude -p`의 JSON 출력을 직접 파싱하는 대가를 치렀다 — CLAUDE.md의 "별도 계측 스크립트를 새로 만들지 않는다" 원칙에서 벗어난 명시적 예외다. 이 하네스 제약("파견된 서브에이전트"로만 스킬을 켜려 한 것)이 원래 질문(스킬이 실제로 프로세스를 개선하는가)과는 무관하다는 게 이 전환의 근거였다.

## 결과

| 지표 | OFF | ON | 차이 |
|---|---:|---:|---:|
| cost_usd | 0.3416 | 0.4897 | **+43.4%** |
| duration_ms | 66,074 | 88,252 | **+33.6%** |
| num_turns | 13.7 | 18.0 | **+31.7%** |
| total_tokens | 25,115 | 34,690 | **+38.1%** |
| 근본 원인 수정(COLLATE NOCASE) | 3/3 | 3/3 | 차이 없음 |
| 회귀 테스트가 실제로 버그를 잡는지 | 3/3 | 3/3 | 차이 없음 |
| RED→GREEN 별도 커밋 | 0/3 | 1/3 | 약한 신호 |

**정성적 근거**: ON-1은 세션 종료 보고에서 "세션에 주입된 `using-superpowers` 훅이 '버그 수정 요청 → systematic-debugging 먼저'를 강제하고 있었고, 이 요청도 정확히 그 케이스였기 때문"이라고 스킬 호출 이유를 정확히 설명했고, 실패 테스트 커밋(`2e6d68f`)과 수정 커밋(`0c0b641`)을 분리했다. ON-2도 같은 이유로 `systematic-debugging`의 4단계 프로세스(Root Cause → Pattern → Hypothesis → Implementation)를 적용했지만 커밋은 하나로 합쳤다. ON-3은 훅의 요구를 인지하고도 "원인이 코드 두 곳만 읽으면 바로 확정되는 단순한 케이스"라 "다단계 가설-검증 절차가 이 정도 난이도엔 과했다"고 판단해 스킬 없이 직접 처리했다 — 스킬을 맹목적으로 따르지 않는 판단력을 보인 사례다. OFF 3세션은 전부 스킬 자체가 없었으니(카탈로그에 없음) 스킬 사용 여부를 판단할 필요조차 없었고, 셋 다 원인을 바로 찾아 수정+테스트를 한 커밋으로 남겼다.

## 결론

**정확성은 superpowers와 무관했다.** 이 버그(SQLite collation이라는 잘 알려진 단일 원인, 파일 하나 안에서 확인 가능)는 강한 모델이라면 스킬 없이도 근본 원인을 정확히 찾았다 — OFF/ON 6/6 전부 옳게 고쳤고 회귀 테스트도 전부 진짜였다. 이 실험만으로는 "결과 품질을 끌어올린다"는 근거를 찾지 못했다.

**프로세스는 실제로 달라졌다.** SUBAGENT-STOP도, 코칭도 없이 진짜 최상위 세션에서 자발적으로 스킬 체인이 작동하는 걸 확인한 게 이 실험의 핵심 성과다 — 훅이 주입한 "버그 수정 → systematic-debugging" 규칙을 3세션 중 2세션이 스스로 인지하고 근거로 들며 따랐다. 다만 그 대가로 비용·시간·토큰이 30~43% 더 들었다 — ponytail 실험에서 본 것과 같은 패턴("프로세스/코드는 개선되지만 총비용은 늘어난다")이 여기서도 재현됐다.

**"프로세스가 실제로 개선되는가"라는 핵심 질문에는 조건부로 "그렇다"고 답할 수 있다.** 다만 이번 버그는 난이도가 낮아 그 개선이 눈에 보이는 산출물 품질 차이로 이어지지 않았다 — 원인이 여러 컴포넌트에 걸쳐 있거나 그럴듯한 오답(symptom fix)에 빠지기 쉬운, 더 어려운 버그였다면 결과가 달라질 가능성이 있다. `systematic-debugging` 스킬 자체가 "다중 컴포넌트 시스템"을 위한 절차를 별도로 갖추고 있는 걸 봐도, 이 스킬이 겨냥하는 상황은 이번 실험보다 더 복잡한 쪽이다.

## 한계

- **표본 크기**: n=3. "RED→GREEN 분리"(1/3), "스킬 의도적 생략"(1/3) 같은 개별 사례성 관찰은 반복을 늘려야 안정적인 비율로 볼 수 있다.
- **버그 난이도 천장 효과**: 원인이 단일하고 잘 알려진 버그라 스킬의 가치가 드러나기 어려운 조건이었다.
- **`claude -p` 전환의 대가**: `Agent` 도구의 자동 계측을 포기하고 직접 JSON을 파싱했다 — CLAUDE.md 원칙의 명시적 예외이며, `cost_usd`(캐시 할인까지 반영된 CLI 자체 계산값)를 가장 신뢰할 수 있는 단일 지표로 취급했다.
- **정성 판정**: 근본 원인 수정·회귀 테스트 유효성은 diff·재실행으로 직접 검증했지만, "프로세스가 개선됐다"는 종합 판단은 세션 자기보고와 `git log` 교차검증에 의존한다.
- 전체 방법론 노트와 세션별 원자료는 [`superpowers.md`](superpowers.md) 참고.
