# 실험 보고서 — ponytail은 토큰을 정말로 줄여주는가

**날짜**: 2026-08-12 · **대상**: [ponytail](https://github.com/dietrichgebert/ponytail) (plugin) · **Archetype**: 코드 생성/볼륨 · **픽스처**: `fixtures/bookmarks-api`
**원자료**: [실험설계](../design/ponytail.md) · [실행별 지표 전체](ponytail.md)

## 한 줄 요약

**토큰 사용량은 줄지 않았다(오히려 소폭 늘기도 했다). 그러나 코드량(LOC)은 -34~49% 줄었고, tool_uses도 -6~8% 줄었다.** ponytail은 "짧은 코드"를 만드는 데는 이 실험에서도 확인됐지만, 그 코드를 만들기 위한 추론·설명에 드는 토큰까지 합치면 저장소가 광고하는 "~22% 토큰 절감"은 재현되지 않았다.

## 핵심 질문과 방법

**핵심 질문**: ponytail을 켰을 때 신규 기능 구현에 드는 토큰 사용량이 실제로 줄어드는가?

- **픽스처**: 최소 FastAPI + SQLite 북마크 관리 API (`bookmarks-api-baseline` 태그로 고정)
- **티켓 A**: 북마크 태그 추가 + `?tag=` 필터링
- **티켓 B**: 북마크에 리마인드 날짜(`remind_at`) 추가 — ponytail 저자 벤치마크의 date-picker 사례를 이 픽스처에 맞게 옮긴 티켓
- **조건**: OFF(ponytail 꺼짐) vs ON(ponytail 켜짐), 두 조건 모두 `caveman`(별개의 프로즈 압축 스킬)은 꺼서 변수를 하나로 격리
- **표본**: 티켓당 OFF/ON 각 3회, 총 12세션(유효 데이터 기준)
- **주 지표**: `subagent_tokens` · **보조 지표**: `tool_uses`, `git diff` 기준 LOC
- 모든 세션은 `bookmarks-api-baseline`에서 분기한 격리 git worktree에서 독립 실행

## 진행 중 만난 두 가지 함정과 대응

실험을 곧이곧대로 한 번만 돌렸다면 잘못된 결론(“ponytail은 효과가 없다”)에 도달했을 것이다. 두 가지 문제를 발견하고 바로잡은 뒤에야 신뢰할 수 있는 결과를 얻었다.

**1) 첫 번째 티켓(태그+필터)은 애초에 ponytail이 잘라낼 게 없는 작업이었다.**
1차 실행 결과가 예상과 반대로 나와 ponytail 저자 자신의 실사용 벤치마크(실제 오픈소스 FastAPI+React 저장소 대상)를 다시 확인했더니, 저자 데이터에서도 **순수 backend CRUD 작업은 on/off 차이가 거의 0%**였다. 효과는 에이전트가 커스텀 UI 컴포넌트/라이브러리를 설치하려는 지점(예: date picker, color picker)에 집중돼 있었다. 우리 티켓 A는 정확히 그 "차이 없는" 유형이었다 — 실측으로도 6개 실행 전부 의존성 변경이 0건이었다. 그래서 저자 벤치마크의 date-picker 사례를 옮긴 **티켓 B**를 추가로 설계해 재실험했다.

**2) 전역 설정을 켜는 것만으로는 서브에이전트에 ponytail이 실제로 켜지지 않았다.**
이 실험은 플러그인을 `~/.claude/settings.json`에서 on/off 토글하고, 그 상태에서 격리된 서브에이전트(worktree)를 띄워 작업시키는 방식으로 설계됐다. 그런데 진단해보니 **설정값 자체는 서브에이전트에 정확히 전달되지만, 플러그인의 "항상 켜짐" 룰셋(SessionStart 훅 기반 자동 주입)은 이 방식으로 스폰한 서브에이전트에는 전혀 전달되지 않았다.** 결과적으로 티켓 A·B의 1차 ON 실행 12세션은 전부 사실상 "off vs off" 비교였다. 프롬프트에서 `Skill` 도구로 ponytail을 명시적으로 호출하도록 지시하는 우회책이 통한다는 걸 확인한 뒤, ON 조건만 이 방식으로 재실행했다(OFF 데이터는 애초에 아무것도 켜지 않았으므로 그대로 유효해 재사용).

이 두 번째 문제는 ponytail만의 문제가 아니라 **이 실험 하네스 전체의 구조적 한계**로 보여, 앞으로 같은 방식(전역 설정 토글 + `Agent(isolation:"worktree")`)을 쓰는 superpowers·claude-mem 실험에도 영향을 줄 수 있다는 걸 `CLAUDE.md`에 기록해뒀다.

## 결과

### 정량 지표 (OFF vs ON, 활성화가 실제로 확인된 데이터 기준)

| 티켓 | subagent_tokens | tool_uses | LOC 삽입(+) |
|---|---|---|---|
| A (태그+필터) | 52,724 → 53,126 (**+0.8%**) | 22.0 → 20.7 (**−6.1%**) | 175.3 → 89.0 (**−49.2%**) |
| B (리마인드 날짜) | 49,244 → 53,533 (**+8.7%**) | 24.7 → 22.7 (**−8.1%**) | 154.3 → 101.3 (**−34.4%**) |

LOC 감소 폭(−34~49%)은 ponytail 저장소가 자체 발표한 "~54% less code"와 근접한 수준이다. 반면 토큰은 A에서 거의 그대로, B에서는 오히려 8.7% 늘었다.

### 정성적 근거 — 실제로 더 가벼운 설계를 택했다

ON 조건에서만 관찰된 구체적 행동 변화:

- **티켓 A**: OFF는 6세션 전원이 태그를 `tags`/`bookmark_tags` **join 테이블**로 구현했다. ON은 3세션 중 2세션이 **콤마로 이어붙인 문자열 컬럼** 하나로 구현했고, 그중 하나는 코드에 `ponytail:` 주석으로 "이 방식의 한계와 언제 정식 테이블로 바꿀지"를 직접 남겼다. 나머지 1세션은 join 테이블을 택했지만 "콤마+부분일치 방식은 태그명에 콤마가 들어가거나 `art`가 `cart`에 오탐되는 등 엣지케이스에서 부정확하다"는, ponytail 규칙("같은 크기의 두 선택지면 정확한 쪽을 택하라")에 따른 명시적 근거를 댔다.
- **티켓 B**: OFF는 대부분 범용 편집 엔드포인트(PUT, url/title/remind_at을 한번에 교체)를 만들었다. ON은 3세션 중 2세션이 **리마인드 날짜 하나만 다루는 좁은 PATCH 엔드포인트**를 만들고 "일반 편집 기능은 실제로 필요할 때 추가"라고 명시했다.
- 두 티켓 6세션 전부, 네이티브 `<input type="date">`를 쓰고 커스텀 날짜 라이브러리는 설치하지 않았다 — 다만 이건 **OFF 조건에서도 동일**했다(아래 한계 참고).

## 결론 — 언제 효과가 있고, 언제 없는가

**효과가 있었던 조건**

1. **코드량과 설계 범위를 줄이는 데는 확실히 효과가 있다.** 같은 기능을 더 적은 코드로, 더 좁은 스코프로 구현했다 — join 테이블 대신 단일 컬럼, 범용 CRUD 대신 요청받은 필드만 다루는 좁은 엔드포인트. LOC -34~49%는 저자 주장과 근접했다.
2. **"두 구현이 동급일 때 더 단순한 쪽을 택하는" 결정 지점이 실제로 있는 작업**에서 차이가 뚜렷했다(티켓 A의 태그 저장 방식, 티켓 B의 편집 엔드포인트 범위). 반대로 이런 갈림길이 없는 순수 CRUD 확장(예: 저자 벤치마크의 "search items by title" 같은)에서는 애초에 잘라낼 게 없어 효과가 거의 없다 — 이건 저자 스스로도 인정하는 지점이다.
3. **강제로 확실히 활성화됐을 때만 효과가 난다.** 이 점이 이번 실험에서 가장 크게 배운 부분이다 — 플러그인을 "설치해서 켜두기만" 해서는 (적어도 이 서브에이전트 실행 방식에서는) 아무 효과도 없었다. 실제 룰셋이 로드됐는지 확인이 안 된 상태의 "on"은 사실상 "off"와 같다.

**효과가 없었거나 반대로 나온 조건**

1. **토큰 사용량 자체는 줄지 않는다(오히려 늘 수 있다).** 코드는 짧아졌지만, `ponytail:` 주석·"skipped: X, add when Y" 요약·YAGNI 래더를 따라가는 사고 과정 자체에 토큰이 든다. 저장소가 스스로 밝힌 한계("추론 모델은 래더를 고민하느라 오히려 토큰이 늘 수 있다")와 정확히 일치하는 패턴이 관찰됐다. **"토큰이 줄어든다"는 주장을 그대로 믿고 비용 절감을 기대하면 안 된다** — 적어도 소규모 백엔드 기능 추가 + 현재 세대 모델 조합에서는.
2. **이미 코드베이스가 최소한이고, 모델 자체가 이미 "게으른" 선택을 잘 하는 경우 효과가 희미해진다.** 우리 baseline은 이미 불필요한 의존성 없이 raw sqlite3로 작성돼 있었고, 리마인드 날짜 UI도 OFF 조건에서조차 전원이 네이티브 `<input type="date">`를 선택했다 — 즉 ponytail이 막으려는 "라이브러리부터 설치하고 보는" 함정에 이 모델은 애초에 잘 안 빠졌다. ponytail 저자의 원 벤치마크는 상대적으로 약한 모델(Haiku 4.5)을 썼고, "더 강한 모델일수록 격차가 줄어들 수 있다"는 걸 스스로 인정한다 — 이번 결과가 정확히 그 방향이다.
3. **활성화가 확인되지 않은 채로 "설치만 해두는" 경우, 실질적 효과는 0이다.** 실사용에서 이 리스크는 사용자에게 그대로 전이된다 — 플러그인이 설정상 켜져 있어 보여도, 실제로 매 세션 룰셋이 주입되는지는 별개 문제일 수 있다.

## 한계

- **표본 크기**: 티켓당 n=3(OFF/ON 각 3회). 저자 벤치마크(n=4×12티켓)보다 훨씬 작다.
- **명시적 호출 조건**: ON-v2 결과는 프롬프트에서 `Skill` 도구를 강제로 호출시킨 조건이다 — ponytail이 광고하는 "설치만 해두면 호출 없이 항상 켜짐"과는 다른 조건에서 측정한 결과다.
- **caveman을 두 조건 모두 꺼둔 것**: 변수 격리를 위한 선택이었지만, 사용자가 실제로 쓰는 조합(ponytail+caveman 동시 사용)과는 다른 상태다.
- **테스트 개수 재량 편차**: 세션마다 추가한 테스트 개수가 달라(6~10개) LOC/토큰 차이의 일부를 설명할 수 있다.
- 전체 방법론 노트와 세션별 원자료는 [`ponytail.md`](ponytail.md) 참고.
